# Project progress

**Scope:** interactive demo of a fictional EA referral workflow, with connected API, repository, auth, file-processing, assessment, notifications, and database code. The current demo mode uses invented data in per-tab memory. Supabase migrations are applied; connected mode is not ready for real applicants because provider setup, Vercel deployment, configured malware scanning, and browser/integration verification remain incomplete.

## Shipped code and remaining work

- **Demo:** candidate and owner screens use fictional fixtures. Demo changes live in per-tab memory and are not durable.
- **Authentication code:** candidate email-code sign-in UI and auth request/verify APIs exist. Connected APIs validate access tokens and check the configured owner identity. Supabase Auth and its OTP email delivery are not configured or integration-tested.
- **Database code:** migrations `20261023201621`, `20261025024815`, `20261025031810`, and `20261025040049` define connected persistence, storage, referral-slot RPCs, indexes, and candidate notification cleanup; all four are applied remotely. Post-apply checks confirmed 10 public tables with RLS and FORCE RLS, 0 table grants to `anon`/`authenticated`, 70 `service_role` table grants, and 15 RPCs executable by `service_role` only. The five previously flagged foreign-key columns are indexed: applications.candidate_id, audit.job_id, events.job_id, outbox.recipient_user_id, and resumes.job_id. Candidate deletion purges persisted notification outbox PII, and enqueue is rejected after candidate deletion; an already in-flight Resend send cannot be recalled. Both privacy triggers are enabled, and their functions are `SECURITY INVOKER` with fixed `search_path=pg_catalog, public`. The unindexed-FK performance advisor findings are resolved; 14 unused-index INFO findings are expected before traffic, and 10 RLS/no-policy security INFO findings reflect deliberate service-role-only grants. Application behavior still needs live integration verification.
- **Application intake:** connected `POST /api/applications` validates verified identity, job/slot availability, resume ownership/readiness, and supporting files before calling the submission RPC. The route and repository exist; provider behavior is not integration-tested.
- **Candidate status:** status APIs require verified identity. Once the configured Auth OTP flow succeeds, candidates can access their own status; separate private status-link delivery and email notifications are not implemented.
- **Resume storage and parsing:** private resume and supporting-file upload routes, configurable scanner client, and bounded extraction for supported text-based PDF/DOCX files exist. PDF operator and font support is limited, so this is not a general PDF compatibility guarantee. The private `ea_referral_resumes` bucket migration is applied with a 4 MiB limit; absent or failing scanner configuration fails closed to quarantine. OCR is not implemented. SQL scopes resume replacement to the authenticated candidate's own job application and permits it only after the owner sets `correction_required`; replacement increments the job-specific version, clears the old readiness and assessment, and routes the application back for review. The candidate correction experience still needs full end-to-end verification.
- **Availability:** manual job state can be stored, but no official EA availability checker is connected. Unknown availability remains ineligible for intake.
- **Funnel metrics:** connected event capture uses HMAC-derived pseudonymous candidate/job keys; the dashboard counts distinct visits/starts/checks from the latest 30 days and application IDs for submissions/referrals. Current capture is limited to role view, intake start, and quick-check pass events.
- **Assessment:** owner-triggered Vercel AI Gateway advisory assessment is implemented. Resume text is redacted for the candidate's direct contact details before sending with the job description; output is validated and does not decide or update an application. `AI_GATEWAY_API_KEY` and operator-selected `AI_GATEWAY_MODEL` are not configured, and no live call has been made.
- **Notifications:** connected preview/send APIs and UI are implemented. Sending requires a current preview, explicit owner approval, `RESEND_API_KEY`, `RESEND_FROM_EMAIL`, and a Resend-verified sender domain. Account/DNS configuration and live delivery remain outstanding. A separate status-link sender is not implemented.
- **Deployment:** no Vercel project setup or production deployment has happened. Provider configuration, browser verification, monitoring, and release review remain outstanding.
- **External sources:** no EA scraping/API, LinkedIn integration, LinkedIn message access, or automated referral submission exists.

## Configuration files

`.env.example` contains placeholders for Supabase server settings and documents the demo default. It contains no secrets. Exact configuration steps and names for the additional server-only scanner, AI Gateway, and Resend variables are documented in [`SETUP.md`](SETUP.md). Setting connected mode alone does not make the system production-ready; Supabase OTP mail/redirect setup, scanner configuration, AI Gateway model/key selection, Resend domain/DNS, Vercel deployment, and browser/integration verification remain outstanding.

## Verification

`npm test` runs domain unit tests and mocked server-contract tests. Server-contract tests replace `fetch` with local mocks; they do not contact Supabase, verify live SQL behavior, send email, call AI Gateway, or constitute end-to-end tests. The applied migrations received post-apply structure/access checks, but connected application flows still need integration verification. No browser verification has been performed.
